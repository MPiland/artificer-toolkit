# ADR 0041: Stored Character Sheet sections

- **Status:** decision (RELIABILITY-21.T16, AC RELIABILITY-21.16 and 21.3)
- **Date:** 2026-10-28
- **Scope:** `apps/apis/convex/characters` (Character writes and Sheet reads), `campaigns/characterSheet.ts`, `packages/schema/src/projections/characterSheetSections.ts`
- **Builds on:** [ADR 0036](0036-versioned-content-snapshots-and-browser-builder.md), whose content-snapshot heads stand for the authored content a Sheet resolves against
- **Verification:** `apps/apis/convex/characters/sheetSections.test.ts` (stored and live parity for owner, GM and party viewers; a stored read's I/O budget; fallback once an input changes outside a Character write; a derivation queued for every assigned Character after a Campaign-scope change; reads while a store is queued, the composed whole Sheet and the superseded-store fence, Amendment 2)

## Context

Every Sheet query re-derived the whole Sheet: it loaded the Character, its sources, the System and every class-list Spell, then evaluated rules (350–400 ms on a level 1 Cleric beside the SRD) to return one slice of 1–24 KB. A Sheet page issues six slice queries plus a panel and preparation query per open surface, and each Sheet command invalidates all of them reactively. In builder-browser and character-sheet-browser the re-derivations queued behind each other until `characters/sheetSlices:get` neared the 1 s query limit and journeys needed reruns.

Projection after derivation costs under 1 ms per section. Rules evaluation does not depend on the viewer; only the viewer projection (visible conditions, display adjustments, private fields) and panel command filters do.

## Decision

1. **A Character write derives the Sheet once and stores it per section.** A write that evaluated the Sheet itself (active sources with their prose) stores in `writeCharacterRecord` through the `storeSheetSections` input. Only the Sheet's own writers pass it: Sheet commands, the GM overlay refresh and the Encounter port, so writers such as content deletion do not load Sheet projection. Every other write of an `ACTIVE` Character queues the internal mutation `characters/sheetSectionDerivation:store` about 300 ms ahead (`CHARACTER_SHEET_STORE_DELAY_MS`). Those writes are a Builder commit, a resolution-scope command and the focused note writes. (Amended 2026-11-08, PERF-6.T4: inspiration and party visibility are now Sheet commands that store inline; the note write still queues, and while a store is queued a slice, panel or preparation miss serves the last stored section, Amendment 2.) A Builder commit evaluates only referenced content (ADR 0036 S7, inside its read budget), so it cannot store a Sheet that needs active sources with their prose. A Character has at most one queued derivation (amended 2026-10-29, RELIABILITY-21.T16). It is recorded in `characterSheetPendingStores` with its scheduled id and a token. A newer queuing write cancels it and queues its own, so a burst of writes derives once. An inline store cancels it, because the queued derivation would only find the sections current. A derivation that started before it could be cancelled sees a newer token and stores nothing. Builder draft saves are not Character writes and queue nothing. Reads before the derivation lands derive live (amended: slice, panel and preparation reads serve the last stored section, Amendment 2). A queued derivation that fails, for example by exceeding the 1 s mutation limit, fails visibly: Convex logs the timeout and marks the scheduled job failed. It also rolls back, so the stored fingerprint stays stale and reads keep deriving live, correctly, until the next Character write stores or queues again. On CI one post-commit store in builder-browser timed out at 1160 ms (BJ 40914047270); its margin is tracked in RELIABILITY-21.T25. Each store projects its one evaluation for each viewer that can read the Character: `CHARACTER_OWNER`; `CAMPAIGN_OWNER` when the Campaign owner is someone else; and `PARTY_MEMBER` slices while "Party can view" is on. For each viewer it stores every slice except Notes, the panel for every target the Sheet lists (`listCharacterSheetPanelTargets`) and the preparation options.
2. **Two tables.** `characterSheetSections` holds one row per `(characterId, viewer, section)` with the section's JSON and checksum. `characterSheetDerivations` holds one row per Character: the input fingerprint and the list of stored section checksums. A write replaces only the rows whose checksum changed, deletes rows that no longer exist and rewrites the derivation row only when its fingerprint or list changed. (Amendment 2 moves the list to its own `characterSheetSectionChecksums` row.)
3. **The fingerprint covers every stored input the derivation reads.** It checksums:
   - the Character document, Sheet state and play checksums;
   - whether a Builder draft exists, and the route id;
   - the System checksum, read from its own row (Amendment 2);
   - the content-snapshot head revision of each source and of the Campaign;
   - only the Campaign fields the Sheet reads (owner, System, status, maturity, attunement override, catalogues), so notebook and counter patches do not miss;
   - the Campaign Character state and currency options;
   - the Character's active and carried rule effects.
4. **Reads serve a stored section only while it is current** (amended: while a store is queued, slice, panel and preparation reads serve the last stored section; Amendment 2). `sheetSlices:get`, `panels:get`, `preparationOptions:get` and the Campaign `panel` and `preparationOptions` queries call `readStoredCharacterSheetSection`. It applies the same authority the derived read applies (`readAuthorizedCharacterSheetState`, plus the party visibility check), recomputes the fingerprint and returns the stored section when it matches. On any miss the query derives live as before, so a miss is slower but never wrong, and the derived path still reports access errors.
5. **Snapshot heads are read current.** An owner's preparation options carry the content-snapshot manifest. Builds finish without a Character write, so a stored read takes the manifest from the current heads (`readStoredCharacterPreparationOptions`). The fingerprint covers only head revisions.
6. **The stream version is added at read.** Every play write bumps it, so stored rows and the fingerprint leave it out and a read sets it from the Character's play record. A write then rewrites only the sections whose content changed: an HP change rewrites each viewer's COMMON slice, bounded at 12 KB per viewer beside the unchanged 800 B play-record budget (`playStateBudget.test.ts`).
7. **A write stores every section, panels included, in its own transaction.** Queuing the panels saved about 54 ms of a Sheet command (305 to 251 ms in convex-test), but it was tried and reverted. The queued store re-evaluated the whole Sheet and rewrote the derivation row. That second invalidation reran every subscribed slice read, and under CI load those reads hit Convex's 1 s query limit. The Sheet editor then held a stale stream version and its next command was rejected (vtt-browser run 40756050318). A store serializes each section once, with plain `JSON.stringify`, and checksums that string. Projection builds each section in a fixed key order, so a checksum is stable across derivations; canonical JSON cost about 5 ms of each command for no gain (RELIABILITY-21.16). The store fingerprints the row the write produced instead of reading the Character back. A trial on 2026-10-29 (RELIABILITY-21.T16) moved Sheet commands to the queued derivation as well, and it was reverted. Commands got cheaper: `sheetCommands:execute` went from 468 / 1123 ms to 434 / 932 ms, median / max. Play commands come more than the 300 ms delay apart, though, so each still paid a whole derivation, and the vtt store ran at 915 / 1062 ms. About half the vtt slice reads landed in the gap and derived live, at 780 to 1009 ms against 357 ms stored (BJ 40910806558).
8. **Not stored.** The Notes slice (private, read without sources; the whole Sheet's per-viewer notes are stored, Amendment 2); the Proficiencies panel (it resolves the whole catalogue); panel targets the Sheet does not list (cast-level and passive entries); and the panel of a listed Spell the Character does not reference (a full-list Spell not learned or prepared), since the Sheet evaluates only referenced Spells (`collectCharacterReferencedSpellIds`). These always derive live.

## Amendment 1 (2026-11-07, D215): Campaign-scope changes queue a derivation

Approved by the user on 2026-11-07 (RELIABILITY-21.T33). A Campaign-scope fingerprint input no longer leaves its Characters' sections stale until their next write: the mutation that changes it queues the derivation of every Character assigned to the Campaign (`scheduleCampaignCharacterSheetSections` in `characters/sheetSectionStores.ts`). The derivation is deduplicated per Character through `characterSheetPendingStores`, and the party size bounds it.

**The input list is declared once (RELIABILITY-21.T36).** `characterSheetInputs` in `characters/sheetFingerprintInputs.ts`, beside the fingerprint, names every table the fingerprint reads and, for each, which stores a change queues: that Character, a Campaign's party, or the USER source owner's Characters. `lib/mutations.ts` registers one trigger per declared table, so every tracked write queues in its own transaction and a new write path needs no call of its own. Each Character and each Campaign is queued once per transaction. The structural test (`sheetFingerprintInputs.test.ts`) records the tables a personal and a Campaign fingerprint read and fails on any table missing from the declaration. Each trigger queues only when the write moves what the Sheet reads: an insert or delete, or a change in the fields named below. The declaration:

- the Character head, while the Character is or becomes ACTIVE (a DRAFT-status Character has no Sheet): that Character;
- its build state when the row's checksum moves, any change to its collection rows, and its route id while it is ACTIVE (a new Character's route and draft exist before its Sheet): that Character;
- its play state, only when the play checksum moves (the stream version and stored stats are outside the fingerprint);
- an ACTIVE Character's draft insert or delete, since the Sheet shows whether one is open; a draft save queues nothing;
- an active rule effect: its owner and, while it carries Concentration, its caster;
- the Campaign Character state when its checksum moves, and any change to the assignment: that Character;
- the Campaign fields the Sheet reads (`characterSheetCampaignFields`), the currency systems, and an owner's membership status or role: the Campaign's party;
- a content-snapshot head revision: the Campaign's party for a Campaign head (a share or unshare, a membership, System, owner or catalogue change), and the owner's Characters in that System for a USER source head;
- a USER source record: its owner's Characters in that System;
- not queued, with the reason recorded in the declaration: Campaign deletion jobs (authority refuses every read while one runs, and its assignment deletes queue each Character), and Systems and platform catalogues (they change only when a deployment seeds them).

**Cost per write.** Registering a table makes convex-helpers read the written row again: two gets for each patch or replace (before and after), one for each insert or delete. A declared table pays this on every tracked write, queued or not, and a queued write adds its target lookup and one pending-store row per Character per transaction. Draft autosave pays the two gets of the draft head (no payload read). A publish pays the two gets of its content-snapshot head plus the source lookup, three documents. The budget tests (`draftSaveBudget.test.ts`, `publicationReadBudget.test.ts`) state those reads exactly.

Every tracked mutation loads the declaration and the queued store, so both stay in small modules that import no derivation code. Only `untrackedInternalMutation` skips the triggers, and its checkpoint publish and rollback wrap their writes in the tracked database, so live-table checkpoint writes queue too.

**Write rates (RELIABILITY-21.T36).** No input is written near once a second per Character in encounter play, so the 300 ms cancel-and-reschedule debounce needs no cheaper key. The room writes play state, effects and Characters only in checkpoint transactions (lifecycle moments, plus a backlog checkpoint every 200 chat entries or roll cards: at 10 to 30 cards a minute, one every 7 to 20 minutes), one store per Character per checkpoint. Sheet commands are one per click, and their inline store cancels the queued one. Builder autosave updates the draft, which queues nothing. An authoring save or publish is an explicit action that queues each of the owner's Characters in that System once.

A Campaign change queues its party as a chain, so at most one of the Campaign's stores runs at a time. Each assigned Character without a pending store gets a pending row carrying the `campaignId` and no job. The first row is scheduled after the usual delay. Each store, once it commits, starts the next waiting row. Parallel stores contended on the same Campaign rows and multiplied each other's facts and commit time 3 to 5 times, and 2 of 42 timed out (run 42389041471). A Character whose store is already pending is left alone, because that store has not committed and will read the change. A Character write that replaces a chain row's store keeps the row's `campaignId`, and deleting a Character clears its row the way a landing store does, so neither stalls the chain.

Opening or discarding an edit draft over an active Character queues a store, because the fingerprint and the Sheet carry whether a Builder draft is open. Draft saves still queue nothing.

Every scheduled store has a check, scheduled 2 s after the store is due (`characterSheetPendingStores.checkId`):

- a store that lands cancels its check, so a normal store costs no extra function call;
- a store that fails or times out rolls the cancel back, so the check runs;
- while the store is still pending or running, the check looks again;
- a failed or canceled store whose pending row is still current is queued once more (`retried`);
- after a second failure the row is dropped and logged, the sections stay stale (reads derive live until the next write), and the chain moves on.

The queued store reads its inputs once: the authorized Character state, System, sources and effects that decided whether it runs are reused by the facts load and by the write. The pending-store shape changed, so local data is reset after merge (D196).

## Amendment 2 (2026-11-08, PERF-6.T4): reads while a store is queued, the whole Sheet, the System checksum

Ruled by the orchestrator on 2026-11-08 (PERF-6.T4, AC PERF-6.2; option A, option 1 and fix 8 of the ruling packet).

**Slice, panel and preparation reads serve the last stored section while a store is queued.** `readStoredCharacterSheetSections` (in `characters/sheetSections.ts`) takes `whileQueued`. When it is set and the Character has a `characterSheetPendingStores` row, the read skips the fingerprint and serves the viewer's stored section, stamped with the current stream version. Authority and party visibility are checked as before. With no pending row, a moved fingerprint still misses and the query derives live. So an input that changes without queueing a store, such as a platform seed or a raw patch, is never served stale. `sheetSlices:get`, `panels:get`, `preparationOptions:get` and the Campaign `panel` and `preparationOptions` queries pass it. The gap lasts until the queued store lands, about `CHARACTER_SHEET_STORE_DELAY_MS` plus the store. A miss with a store queued reads at most 20 documents and derives nothing (`sheetSections.test.ts`).

Commands are not affected. A Sheet command loads and validates against the stored Character, not the served section. A command sent in the gap uses the stream version that was served, which is the current one, so it runs against the written state (`sheetSections.test.ts`, "runs a Sheet command sent while a store is queued").

**The whole Sheet composes its stored slices.** `characters/sheet:get` and `campaigns/characterSheet:get` call `readStoredCharacterSheet`. While the fingerprint matches, it reads the viewer's six stored slices and a stored `NOTES` section, and composes them with `composeCharacterSheet` (`packages/rules-runtime/src/character/sheetSlices.ts`). The `NOTES` section is the viewer projection's notes, so redaction matches the live read. Otherwise the read derives live. It never serves a queued store, because live proofs read the whole Sheet once, right after a write. The FEATURES slice now carries the whole `resources` (items and hit dice), so the slices hold everything the Sheet does. This is a stored-shape change, so local data is reset after merge (D196).

**The fingerprint reads a System checksum row.** `systemChecksums` holds one row per System, `{ systemId, checksum }`, indexed `by_systemId`. Only the content bootstrap (`content/import.ts`) writes it, when it upserts the System. The fingerprint reads it with an index point lookup instead of the 34 KB System document. Like the System, it is declared `unqueued` in `characterSheetInputs`.

**A read loads only the fingerprint.** `characterSheetDerivations` now holds `{ characterId, fingerprint }`. The list of stored section checksums, which covers every viewer and panel (about 17 KB for the fixture Character), moved to `characterSheetSectionChecksums`, and only a store reads it. A store writes the rows, the list and the fingerprint in one transaction and deletes the rows it no longer derives, so every stored row belongs to the stored derivation, and a read no longer cross-checks a row's checksum against the list. A stored slice hit reads at most 40 KB (`sheetSections.test.ts`).

**Why the store cannot overwrite a newer one.** Four rules keep it safe:

- A newer queuing write replaces the pending token, and `deriveAndStoreCharacterSheet` returns when `pending.token !== token`.
- The store also returns when the stored state is already current.
- Convex OCC orders the store's fingerprint reads against any concurrent write, and a conflicting write retries the store over the new state.
- The store settles the pending row in the same transaction that writes the sections.

So the served section is always the last stored one, and a store always derives from the inputs its own transaction read (`sheetSections.test.ts`, "drops a superseded store").

## Consequences

- A Sheet read touches no authored content: it reads authority rows, the fingerprint inputs and one section.
- Writes do more work (one projection per viewer and section, and the changed rows). Most already evaluated the Character; the others pay one scheduled derivation. A Sheet command evaluates once to validate the command; its write reuses that evaluation's source context, so authored content is read once per command.
- Accepted residuals, each a correct live fallback until the next Character write:
  - a write that queues the derivation, until that derivation runs: the whole Sheet derives live, and slices, panels and preparation options serve the last stored section (Amendment 2);
  - an SRD reseed changes the fingerprint of every Character in the System. Campaign-scope changes, USER source edits and their published content, and live-table checkpoint writes queue a derivation instead (Amendment 1).
- Derivation trusts verified documents (RELIABILITY-21.T25, AC RELIABILITY-21.20). Publish and seed parse a publication or System document once, before they checksum and store it. A Sheet derivation verifies the stored checksum and uses the typed document without parsing it again; a mismatch is refused. The parse was about 20 of 72 ms of CPU per store locally (publication about 13 ms, System about 7 ms), 5 to 6 times that on CI. The queued store also reuses the fingerprint it read to decide whether to run, so it fingerprints the Character's inputs once instead of twice. On CI (BJ 41144697084 against the phase tip, BJ 41144699479), median / max: `characterSheet:execute` in vtt 596 / 913 to 370 / 407 ms, `sheetSlices:get` in vtt 295 / 361 to 198 / 394 ms, the account-deletion store 552 / 1051 to 463 / 697 ms and `sheetCommands:execute` there 478 / 916 to 418 / 740 ms. The post-commit Builder store's read volume is not trimmed here: Spell roots are most of it (a local Cleric store read 567 KB, 386 KB in roots), and cutting it moves `authoringSources` off `authoredRoots`, a stored-shape change tracked in its own task.
- No migration: pre-launch local data is reset after merge (D196). A Character without stored sections reads live until its next write.
