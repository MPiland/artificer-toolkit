# Slice RELIABILITY-17: unseen-target Worker test is deterministic

Workbook rules: [slice-workbook-rules.md](slice-workbook-rules.md).

## Scope

- Closes AC RELIABILITY-17.1. nativeRoomUnseenTarget.test.ts "takes a creature the map draws, with nothing revealed" (ATTACK-17.3) intermittently gets an empty target list (ci/reaction-4-t3b Tests 38877353496 attempt 1). Find the cause and fix it there: no retry, no weakened assertion.
- Prove with a forced red on `ci/reliability-17-red` and green on `ci/reliability-17`, both cut from the newest `origin/ci/merge-batch-*`.

## Log


- Cause: the Worker fixtures wait for the room's first reply (the owner's first STATE_SYNC, which the room sends only after it has built the presented Scene inside the Durable Object; the target-list and command answers behind it) with `vi.waitFor`'s 1 s default, and the test itself has Vitest's 5 s default. A loaded runner takes longer than 1 s to build the room, so the wait gave up with no frames received and the assertion saw `[]`. Evidence: the failing run's `messages` were entirely empty after the wait.
- Fix (test platform only, no product code): `ROOM_REPLY_WAIT` (20 s) in `liveRoomFixture.ts` is passed to every room-reply `vi.waitFor` in `liveRoomFixture.ts`, `actionRoomFixture.ts` and `movementRoomFixture.ts`; `vitest.config.ts` raises the Worker `testTimeout` to 30 s so the wait is bounded by the test. A room that never answers still fails the test. No retry, no assertion changed.
- Forced red: on `ci/reliability-17-red`, a 1.5 s delay in the fixture's Scene-read mock on the unfixed base failed 627 tests with the exact assertion error, including all four in `nativeRoomUnseenTarget.test.ts` (Tests 38881892455, `f088f07d8`). The same delay with the fix, narrowed to the target file, is green (Tests 38887833062, `38fa1a425`). The first fixed attempt delayed the whole suite and hit the 30-minute job timeout (cancelled Tests 38884216816), which is why the delay was narrowed.
- Risk: the cause is proved by exact reproduction at the failure site, not by timing observed on the original flaky run. A test that legitimately takes longer than 1 s per reply now passes instead of failing early; a real hang fails at 20 s per wait.
- Second cause (found when the first fix still flaked: Tests 38889739986, `nativeRoomSheetHealEndsGrant`, an empty wait the full 20 s): every room in a test file shares one `globalThis.fetch`, and each fixture replaces its implementation. A room an earlier test left draining checkpoints through the next test's Convex mock, and that mock's `/live-sessions/checkpoint` branch recorded the body's sequence and checksum with no `campaignId` check. The next room's bootstrap then read another room's persisted authority, disagreed with its own state, and never activated, so no STATE_SYNC came. The fixture now checks the checkpoint body against its own `campaignId` before it records anything (`liveRoomFixture.ts`).
- Regression test: `nativeRoomFixtureIsolation.test.ts` builds a foreign checkpoint body itself and sends it through the next fixture's fetch. Red on `ci/reliability-17-red3` (Tests 38894485983, `1fbdc8089`, no guard): the room never reaches STATE_SYNC, with the exact `expected [] to deep equally contain ObjectContaining{…}`. Green on `ci/reliability-17` (Tests 38894481673, `c85692fdd`). An earlier red/green pair (red2 38892078328, green 38892132802) used a capture of the room's own checkpoint, which the room does not always send; the test was rewritten to build the body.
- Risk: the leaked-room path is proved by replaying a foreign checkpoint, not by observing the original flake's own leak; the log (a DRAIN checkpoint at the failing test's start) matches it. If another flake with an empty STATE_SYNC wait appears, look first for another unguarded mutation in the shared fetch mock.
