# ADR 0035 S0 measurements, 2026-09-27

**Status:** decision-gate evidence for slice S0 of the
[ADR 0035 implementation plan](../../handoffs/adr-0035-implementation-plan.md). This is a spike: no
product source changed. It answers the plan's open measurements and recommends N, the lease and the
preview fix. It is not acceptance evidence, and the ledger is unchanged.

**Headline.** Room CPU and Durable Object limits are not the problem. Convex database I/O is, and it
cannot be fixed by choosing N: the problem is the shape of the records a checkpoint writes. With
today's documents, no N fits the free plan, not even one checkpoint per session. With the three
shape changes below, N = 120 s fits 1 GB a month, but without Q16's 50% headroom. Transient previews
break two Durable Object daily limits on their own, and must change whatever else happens.

## Method

Base: `codex/phase-08-2-convex-cutover` at `b09c6bbb9`, clean tree. The spike code, logs and fixtures
are under ignored `local-validation/adr35-s0/`. Every test and Wrangler run held
`local-validation/.validation.lock`. No cloud deployment and no Docker were used.

- **Write sets** (`convex/writeSets.spike.ts`, `recorder.ts`). This is convex-test with the apps/apis
  harness. Each Encounter command runs through the room path (`executeInRoom`, which uses the real
  Worker planners with Convex served in process). Every app table is snapshotted before and after
  each command. The diff gives each document's operation, its size before and after, its changed
  fields, and the changed top-level keys inside each `*Json` field. Sizes are UTF-8 JSON bytes.
  - **Shapes.** One Character, and the V15 workload Creature (`createCutoverWorkloadCreature`)
    filling the rest of the Run, at 11 and 100 actors. The Run runs in Assisted mode with auto-roll
    on, then START and the initiative-order choices. After that come the V15 turn items: two fixed
    actions and one end of turn per Creature turn (13 turns at 11 actors, 8 turns at 100), and two
    GM tools (`UPDATE_ACTOR`, for hit points and for controllers).
  - **Moves.** The bound move and its opportunity-reaction response use the V15 movement proof
    shape from `developmentLifecycle.test.ts`, with 11 and 100 enemies.
  - **Sessions.** The fixture sessions were extended past their 60 s expiry, because the recorder's
    snapshots slow the run.
- **Route capture.** The same run recorded every Worker → Convex route call (request and response)
  for START, three actions and two turns at each shape. These are the "inputs captured once".
- **Room CPU** (`worker/*.bench.test.ts`, `vitest.worker.config.ts`). This runs in local `workerd`
  through `@cloudflare/vitest-pool-workers` 0.21.3 with the session Worker's DO binding.
  - The recorded responses are replayed by a stubbed `fetch`, in order, and the unmodified
    `executeLiveEncounterCommand` runs against them.
  - "Transport" replays only `callLiveSessionRoute` for the same calls: input parse and stringify,
    plus response parse. This is the part S6 deletes.
  - Each bench file runs in its own vitest process, so its first call is in a fresh isolate. The
    whole set ran twice (r3 and r4); both runs are reported.
  - Startup comes from `wrangler check startup` (local).
- **Room store prototype** (`worker/d-storage.bench.test.ts`). SQLite in a real DO holds the
  snapshot chunks (128 KiB, the size the journal uses), one log row per command, compaction, and a
  one-row-per-record alternative. It also runs the exact upsert from
  `NativeSocketTransientState.retain`. Rows come from `SqlStorageCursor.rowsRead` and `rowsWritten`,
  as Cloudflare bills them.
- **Checkpoint model** (`summarize.mjs session`). A 4-hour session is the full V15 command mix:
  848 commands (2 × 8 rounds of 11-actor turns: two actions, a bound move, its reaction response,
  and the end of turn), evenly one every 17 s.
  - Changed documents are coalesced per window, and the last version wins.
  - A Convex write costs the whole new document, because Convex writes whole documents even for a
    patch. A patch also reads the prior version.
  - Assumed extras: 300 B of index entries per written document, and a 1.4 KB authority fence read
    and write per checkpoint.
  - Monthly totals use Q16's load model: 20 tables × 4 sessions = 80 sessions.

## 1. Room CPU in local workerd

The machine is a local Windows desktop CPU. It is not Cloudflare's, so use the ratios and the order
of magnitude, not the absolute milliseconds.

**The clock was not frozen locally.** A 50 ms busy loop measured 50 ms inside synchronous code. So
local `performance.now()` is valid for these benches. In production, timers only advance on I/O, so
production CPU must come from Cloudflare's metrics (tail events or analytics), not in-code timing.

**(a) One command, planned from captured inputs.** Values are ms, run r3 / run r4. Warm is the p50
and p95 of 40 runs.

| Command | Actors | Captured inputs | Cold (first call) | Warm p50 | Warm p95 | Transport (warm p50) | Planning without transport |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `RESOLVE_ACTION` | 11 | 15 rules captures, 149 KB | 176 / 125 | 26 / 16 | 34 / 20 | 6 / 5 | about 11–20 |
| `ADVANCE_TURN` | 11 | 14 captures, 156 KB | 49 / 28 | 23 / 15 | 34 / 16 | 6 / 4 | about 11–17 |
| `RESOLVE_ACTION` | 100 | 104 captures, 1.10 MB | 255 / 196 | 103 / 84 | 133 / 105 | 28 / 27 | about 57–75 |
| `ADVANCE_TURN` | 100 | 103 captures, 1.17 MB | 181 / 133 | 144 / 118 | 161 / 139 | 29 / 28 | about 90–116 |

- **JIT behaviour.** The first action in a fresh isolate costs 100–150 ms more than warm. The first
  turn afterwards is already close to warm, because it shares most of the code. The planners are
  warm after 2–5 calls. The first warm sample (for example 43 / 22 ms against a p50 of 26 / 16) is
  the tail of tiering-up.
- **Module evaluation.** The vitest module runner's import time (6.3–7.4 s) is dominated by Vite's
  transform and transport, so it is not representative.
- **Startup.** `wrangler check startup` gives 40.7 ms of active startup CPU for today's bundle
  (4,385 KiB, 755 KiB gzipped).
- **Planning cost scales with the Run, not only the command.** At 100 actors an action reads a rules
  capture for every actor. After S6, the capture parse (the transport column) goes away, but
  planning is still about 60–115 ms per command at 100 actors. That is well inside the 30 s Durable
  Object CPU limit and the 1 s command budget.

**(b) 100-actor hydrate.** This parses and validates every rules input START reads for the Run
(102 rules captures and 2 Character captures, 946 KB), with the same route contracts, then indexes
them in memory.
- **100 actors:** validation 48–55 ms cold and 20–22 ms warm; indexing 2 ms.
- **11 actors:** 177 KB; validation 4–5 ms; indexing under 1 ms.

**(c) Waking a room from hibernation** (prototype of the S2 store):

| | 11 actors | 100 actors |
| --- | --- | --- |
| Snapshot (rules inputs only) | 177 KB, 2 chunks | 946 KB, 8 chunks |
| Rows written per command (one log row: write set, receipt, checksum; `INTEGER PRIMARY KEY`) | 1 | 1 |
| Log row size (the commit input a planner builds today) | 17 KB mean | 140 KB |
| Rehydrate after 40 unsent commands: rows read | 42 | 48 |
| Rehydrate CPU (read, `JSON.parse`, rebuild, apply 40 write sets) | 2–3 ms | 17–24 ms |
| Compaction at a checkpoint (drop and rewrite chunks, delete 40 log rows) | 44 rows | 56 rows |
| Alternative, one row per record: rows per changed record | 1 | 1 |

- **What the snapshot leaves out.** It holds the rules inputs, not the Encounter state records.
  Adding the Run and its actors (about 9 KB each) roughly doubles the chunks at 100 actors, to about
  15.
- **Worst-case wake.** Isolate startup (about 41 ms, only if the isolate itself was evicted), plus
  rehydrate (3 or 20 ms), plus the first command's JIT penalty (100–150 ms). That stays under
  250 ms.

## 2. Durable Object cost for the V15 workload

**The session.** One room, 1 GM and 5 players, 11 actors, 848 commands, 4 hours, 160 bound moves.
Durable Objects are billed only while a handler runs or awaits I/O; an idle object that can
hibernate is not billed (the Cloudflare pricing page, checked 2026-09-27).

The room uses the hibernation API (`acceptWebSocket`). Its only timers are cleared inside
`callLiveSessionRoute`, and one alarm serves admission deadlines and idle release, so idle time is
not billed.

Previews run at the client throttle of 31 Hz per stream (`CampaignVttStage.tsx`: at most one sample
per 32 ms). The inputs are:
- **Drag:** 160 moves × 1.5 s ≈ 7,500 samples.
- **Pointer:** the room receives `POINTER_PREVIEW` on every pointer move over the map, for every
  member, not only while dragging. Full hover by all 6 members is 6 × 31.25 × 14,400 s = 2.7 M
  samples. The table uses 10% and 50% of that.

| Dimension, per session | Target design (after S6), without pointer previews | Pointer previews at 10% / 50% hover | Workers Free daily limit | Verdict |
| --- | --- | --- | --- | --- |
| **Requests** | About 570 (see below) | +13,500 / +67,500 | 100,000 | Fine without pointers. With them, 7 / 1.5 sessions a day: **fails** at a 10-session peak day |
| **Rows written** | About 2,300 at 11 actors, 3,800 at 100 (see below) | Today +270,000 / +1.35 M; 0 after the fix | 100,000 | Fine after the fix. **Today one hovering member exhausts the day in 53 minutes** |
| **Rows read** | Under 10,000: wakes of about 45 rows, log reads at checkpoints | Today +1 per sample (the `read` before each `retain`) | 5 M | Fine |
| **Duration** | About 115 s active (see below), which is 15 GB-s | Pointer handlers at about 0.5 ms each: +135 s at 10% | 13,000 GB-s | Fine: about 400–800 sessions a day |
| **CPU per request** | 16–26 ms per command (11 actors), 84–144 ms (100) | – | 30 s per request | Fine |

**How the target numbers were built:**
- **Requests:**
  - 12 WebSocket upgrades, including reconnects.
  - (848 commands + 102 AUTHENTICATE + about 100 sync messages) ÷ 20.
  - About 130 alarm invocations: one per checkpoint window at N = 120 s, plus rounds and idle release.
  - 7,500 drag samples ÷ 20 = 375.
- **Rows written:**
  - 848 log rows, and 848 log-row deletes at compaction.
  - About 122 checkpoints × chunk rewrites: 2 + 2 rows at 11 actors, 8 + 8 at 100.
  - About 130 `setAlarm` calls.
- **Duration:**
  - Commands: 848 × about 30 ms = 25 s (at 100 actors, about 130 s).
  - Checkpoints: about 122 × about 300 ms spent awaiting the Convex mutation = 37 s. At N = 30 s it
    is 127 s.
  - Re-authentications: 102 × about 300 ms = 31 s.
  - Drag previews: 7,500 × about 3 ms = 22 s.
  - The preview handler costs are estimates; they were not measured.
- **Today, for comparison:** each command awaits two Convex round trips (V15 p50 about 480 ms), so
  848 × 0.5 s ≈ 424 s, which is 54 GB-s. That is still inside the free plan.

### The transient preview problem (existing, measured)

- **The write.** `NativeSocketTransientState.retain` upserts on every accepted sample: 2 rows for a
  stream's first sample (row plus primary-key index), then 1 row per sample (measured).
- **The rate.** At 31.25 Hz, one continuously active stream writes 112,500 rows an hour. Pointer
  previews are sent on any hover, so a single member moving the mouse over the map exhausts the
  free plan's 100,000 rows a day in about 53 minutes.
- **Requests too.** The same samples are also 1/20 of a request each. At 50% hover by 6 members,
  that is 67,500 requests per session, two-thirds of the daily request limit.
- **Convex calls from previews** (a second existing problem, not measured for bytes):
  - A `POINTER_PREVIEW` refreshes an authority capture (a Convex query) at most every 2 s per
    origin (`#authorityCapture`, `authorityCaptureTtlMs`).
  - A player's `TOKEN_DRAG_PREVIEW` calls `visionRevisions` on every sample when the Scene has
    Character vision (`#visionRevisionsCurrent`, D33).
  - At 10% hover and V15's 160 moves, that is about 4,300 + 7,500 calls per session, or about 0.9 M
    Convex calls a month for 80 sessions, against the 1 M allowance.

**Proposed minimal fix: memory-only previews.**
- **What to change.** Keep the per-socket, per-stream `{sequence, sceneId, baselineVersion, path}`
  in a `Map` on the room instance, and delete the `native_socket_transients` table.
- **Why it is safe.** While samples arrive at 31 Hz the object cannot hibernate, so nothing is lost
  mid-drag. After hibernation (10 s or more of silence), losing the path only means the next sample
  restarts from the token's position, which is already the fallback for a new baseline.
- **The one visible risk.** A sample delayed across a wake could render for a single frame. The
  baseline check already discards anything older.
- **Why not coalesced persistence.** Writing at most once a second per stream is still 3,600 rows an
  hour per stream, so it does not fit.
- **The other two changes.** Both are needed for the request and call budgets, and neither is a
  storage change:
  - Pointer previews should be sent only while the member uses a pointer or ping gesture (Owlbear
    Rodeo's model; Foundry's always-on cursors are a setting), or at 10 Hz or less.
  - S4's cached authorization removes the per-preview Convex calls.

## 3. Checkpoint delta size

### Write sets per command today (median, sizes in KB)

| Command | Actors | Documents | Written (whole documents) | Prior versions read | Changed fields only |
| --- | --- | --- | --- | --- | --- |
| `RESOLVE_ACTION` / bonus action | 11 | 7 | 80 | 49 | 53 |
| `ADVANCE_TURN` | 11 | 7 | 60 | 33 | 28 |
| GM `UPDATE_ACTOR` (hit points or controllers) | 11 | 4 | 66 | 41 | 48 |
| Bound move (`MOVE_SCENE_TOKEN`) | 11 | 7 | 26 | 1 | 25 |
| Reaction response | 11 | 12 | 109 | 56 | 86 |
| `RESOLVE_ACTION` | 100 | 7 | 475 | 248 | 429 |
| `ADVANCE_TURN` | 100 | 7 | 455 | 232 | 224 |
| GM `UPDATE_ACTOR` | 100 | 4 | 461 | 240 | 424 |
| Reaction response | 100 | 12 | 505 | 255 | 462 |
| START (the whole Run's initiative occurrence) | 11 / 100 | 2 | 41 / 304 | 0 | – |
| Each initiative-order choice | 11 / 100 | 2 | 47 / 365 | 46 / 364 | 36 / 322 |

What an action changes:
- **The Run** (`encounterRuns`): `version` and `updatedAt`, rewritten whole. The document is 31 KB
  at 11 actors and 236 KB at 100, because its `projectionJson` embeds every actor (24 KB / 225 KB).
- **Two actors** (`encounterRunActors`, 9 KB each): only `currentHitPoints` (4 B) or `resources`
  (56 B) change inside `stateJson`.
- **A new `encounterRunCommands` row** (26 KB / 227 KB). Its `resultJson` stores the whole GM
  projection for replay.
- **Also written:** an occurrence (0.5 KB), a rule receipt (4.9 KB, of which `resultJson` is
  3.8 KB), and a `sceneVisionRevisions` bump.

A turn changes two `encounterInitiativeParticipants` (0.7 KB each) instead of the actors. The
reaction response adds a 22.6 KB `sceneGeometrySaves` row and a 13 KB receipt.

**So the real change per command is a few hundred bytes. The bytes come from two embedded copies of
the whole Run (the Run projection and the command's `resultJson`) and from whole-document rewrites
of 9 KB actor documents.**

At 100 actors, the fixture's START needed 53 tied initiative-order choices, because every Creature
is identical and the dice are fixed. Each choice rewrote a 365 KB occurrence: about 39 MB of Convex
I/O for one START today. In the room design these choices become room commands, and only the final
lifecycle checkpoint reaches Convex.

### Session totals by checkpoint interval

The model shapes are:
- **Today:** the documents exactly as stored now.
- **Minimal:** no embedded Run projection, no `resultJson` on commands or receipts, no pending
  snapshot on occurrences, and no `sceneGeometrySaves` (room-owned moves do not stage in Convex).
- **Split:** Minimal, plus hot play state in small documents, so a changed record costs 512 B plus
  its delta.
- **Packed:** Split, plus the append-only history (commands, receipts, occurrences) packed into one
  ledger document per checkpoint at about 400 B per entry.

the average checkpoint size.

### Which N fits in 1 GB

- **Today's record shapes: none.** Even a single checkpoint per session costs 2.4 GB a month.
- **Minimal: only rounds only or once per session** (0.67 / 0.33 GB for live play alone).
- **Packed:**
  - **N = 120 s** gives about 0.51 GB with hydrate. That fits 1 GB only if everything outside live
    play stays under about 0.45 GB a month.
  - **N = 300 s** gives about 0.33 GB.
  - Neither meets Q16's 50% headroom (0.5 GB planned in total) unless non-live usage is under
    about 0.17 GB. Non-live usage (Builder, Sheet, lobby, authoring) has not been measured; S9's
    Decision 9 budgets have to measure it.
- **The model is linear in commands.** Sessions with less combat cost proportionally less, because
  a checkpoint is sent only when state changed. The 848-commands-in-4-hours pace is a heavy session.

## 4. Token lifetime and Convex limits

**The access token lasts 15 minutes.**
- **Where it is set.** `apps/apis/convex/betterAuth/options.ts` configures the `convex()` plugin with
  no `jwt.expirationSeconds`. `@convex-dev/better-auth` 0.12.5 then defaults to `60 * 15` s
  (`dist/plugins/convex/index.js:44`).
- **How the room uses it.** The room's admission deadline is the token's `exp`
  (`nativeLiveSessionRoom.ts`, the AUTHENTICATE handler). So each socket re-authenticates at least
  every 15 minutes, with one Convex `capture` per re-authentication.
- **The ticket is separate.** The room ticket lives 60 s (`LIVE_SESSION_TICKET_TTL_SECONDS`) and
  only gates admission.

**Convex transaction limits** (Convex docs, fetched 2026-09-27; installed `convex` 1.45.0,
`convex-test` 0.0.56). A checkpoint mutation must stay under:

| Limit per transaction | Value |
| --- | --- |
| Data read | 16 MiB, including filtered-out data |
| Documents scanned | 32,000 |
| Index ranges (`db.get` and `db.query` calls) | 4,096 |
| Data written | 16 MiB |
| Documents written | 16,000 |
| Document size | 1 MiB |
| Argument or return size | 16 MiB |
| User-code time | 1 s |

What that means for a checkpoint:
- **Today's shapes.** A 100-actor round checkpoint (10.9 MB) fits. A drain or final checkpoint after
  a long unsent period does not (165 MB for a session), so staged parts are required, as the plan
  says.
- **Split and packed.** Every modeled checkpoint stays under 4 MB. The largest, one split checkpoint per session, writes 3,227 documents.
- **Index ranges bind first** for a checkpoint that looks up each changed record by public UUID: at
  most 4,096 records per transaction.
- **The ledger document.** A packed ledger document per round is about 130 KB, well under 1 MiB.

## Recommendations

1. **Change the checkpoint's record shapes before sizing N.** These are S1/S3 contract decisions for
   the architect:
   - The checkpoint writes no embedded Run projection. Convex readers outside the room project on
     read, or the projection is written only at lifecycle checkpoints.
   - It writes no per-command `resultJson`. The replay index keeps a result checksum, and a replay
     across epochs re-projects.
   - Hot play state (hit points, temporary hit points, conditions, resources, action economy,
     current turn) lives in small documents, separate from the 9 KB actor and 236 KB Run documents.
   - Commands, receipts and occurrences are packed into one ledger document per checkpoint.
2. **N = 120 s,** plus every round boundary and lifecycle event (Amendment 4). N = 30 s cannot fit
   1 GB in any modeled shape (0.75 GB for live play at best). Treat N as provisional until S9
   measures non-live usage. If Q16 keeps 50% headroom, N = 300 s, or rounds and lifecycle events
   only, is the fallback. N only bounds staleness outside the room.
3. **Lease 240 s (2N), renewed by checkpoint responses and each socket's 15-minute re-authentication.**
   - The token's 15 minutes does not bind the lease.
   - A 60 s lease would need dedicated renewal reads. Assuming about 10 KB each, one a minute is
     about 2.4 MB per session, or 0.19 GB a month.
   - When the lease has expired, the room does one authorization read before the next command.
   - `INVALIDATE_INPUTS` and `EVICT_USER` remain the primary path. The lease only bounds a lost
     notification after the control route's 5 attempts.
   - This widens the ADR's "about 60 s" revocation backstop, so it needs architect approval.
4. **Previews, now, independent of ADR 0035:**
   - Memory-only transient state.
   - Pointer previews only while a member uses a pointer or ping gesture, or at 10 Hz or less.
   - No Convex call per preview. Until S4, cache vision revisions per scene version.
5. **The S2 store.** One log row per command (`INTEGER PRIMARY KEY`, measured 1 row written),
   snapshot chunks compacted at each checkpoint. This is cheaper in rows than one row per record
   at about 7 records per command.

## Threats to the plan

- **Free-tier Convex fit depends on recommendation 1**, which is a schema and contract change larger
  than "carry deltas": the Run projection and command-result copies are stored today on every
  commit.
- **Pointer previews exceed Durable Object request and row limits today,** and use most of the
  Convex call allowance.
- **Planning at 100 actors costs 60–115 ms of CPU per command,** even with inputs in memory. The CPU
  and latency budgets hold, but S9's per-command CPU budget has to be set per actor count.
- **Duration is modest,** but only while the room stays hibernation-eligible between messages. Any
  future long-lived timer or outbound socket would bill wall-clock time: 1,843 GB-s per 4-hour
  session, which is 7 sessions a day.

## Uncertainty

- **Convex I/O accounting.** Whole-document writes are Convex's documented behaviour. The 300 B of
  index entries per document is an assumption; Convex prices each index as another copy of the
  table, so index-heavy tables could cost more. Reads of prior versions assume the checkpoint
  fetches each record it patches.
- **Session pacing.** The model assumes 848 commands evenly over 4 hours, one room, and the V15
  command mix. Real play is burstier: bursts reduce checkpoint count at a given N.
- **Minimal, split and packed are models,** built from measured field sizes, not implemented
  stores. The compact entry (400 B) and the 512 B record base are assumptions.
- **Local CPU.** Timings are on a local desktop under shared load (r3 against r4 differ by up to
  40%). Production CPU is different and must be read from Cloudflare metrics.
- **Previews.** Preview handler CPU and pointer duty cycles are estimates, not measurements.
- **Worker bundle growth.** Growth after the move was not measured. Today's bundle and startup are
  recorded above as the baseline.
